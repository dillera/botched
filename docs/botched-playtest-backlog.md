## Next — P1: Watch the round unfold

- [x] **B-01 — Visible execution queue (SDL client; accepted after live playtesting).** At the start of each resolved round, show the execution order as a horizontal queue, e.g. for two players in a round starting with P1: `P1(1) P2(1) P2(2) P1(2) P1(3) P2(3)`. Highlight the active entry, then remove/advance it when its action has been shown. The next round rotates priority automatically from the established engine rules. **Do not** use a fixed alternation within every round: priority rotates *by tick*, and the exact order must be derived from the existing engine's rules/events. **Done when:** the displayed queue agrees with `ORDER_EXECUTED` events and all 2–4-player rounds.
- [x] **B-02 — Animate movement and machinery separately (SDL client; accepted after live playtesting).** Replay the *existing ordered event stream* on the client: each order, individual `FORWARD_2` substeps, rotations, pushes, blocked moves; then the conveyor phase; then hazards, disable/respawn and crate/delivery events. Preserve intermediate board state so players see why a `WAIT` robot moves or a robot falls into a pit. Clearly label phase changes. **Done when:** the documented pit scenario visibly shows entering the conveyor, one belt displacement, falling into the pit, and later respawning, with no invented positions.
- [~] **B-03 — Playback pacing and skip (SDL client: skip + speed done; remaining polish deferred by decision — no further animation work planned).** Default to readable, short per-event holds rather than a hard-coded 15–20-second round. Provide a simple fast/normal/skip option; user input can skip animation and jump to the authoritative final snapshot. Animation is purely local and never blocks server progress. **Done when:** two clients can watch at different speeds and still converge to the same server state.

**Execution note:** An *order* is not the same as a *tick*: each tick processes players in priority order, **then conveyors and hazards**. The display queue should include clear machinery/phase boundaries (or a separate phase indicator) after each tick. Use the authoritative event order instead of simulating movement independently. If the current events are insufficient to replay a particular transition accurately, report the exact gap before proposing a server change.

### SDL implementation notes (execution queue + round playback)

*Where:* `apps/ui_playback.{hpp,cpp}` (SDL-free step builder + playback state machine, unit-tested in `tests/test_ui_playback.cpp`) and `apps/sdl_ui.cpp` (drawing). The terminal client is unchanged.

* **B-01 done.** A strip under the board lists `P1(1) P2(1) ⚙ P2(2) P1(2) ⚙ …` (⚙ drawn as a gear). Entries come only from the round's `ORDER_EXECUTED` / `ORDER_NO_OP` / `ORDER_SKIPPED_DISABLED` events plus one machinery entry per tick, so the order is the server's. Tests pin round 1 `P1(1) P2(1) * P2(2) P1(2) * P1(3) P2(3) *`, round 2 `P2(1) P1(1) * P1(2) P2(2) * P2(3) P1(3) *`, and 3-/4-player rotation over whole matches. The live entry is highlighted; finished entries are dimmed with a tick; chips show the order code (`F2`, `W`, `-` for skipped).
* **B-02 essentials done.** The client keeps a local copy of the board (positions, headings, carried crates, scores, damage, belt-group state), starts from the last snapshot and **commits one server event at a time**: `ROBOT_MOVED` / `ROBOT_ROTATED` (turn animates) / `ROBOT_PUSHED` (victims and pusher move together, impact burst) / belt moves (amber trail + gear badge, only in the machinery phase) / `MOVE_BLOCKED` (nudge + red ✕) / pickup, drop, delivery (ring + "DELIVERED!") / `GROUP_TOGGLED` (belts flip and pulse at that moment) / `LASER_HIT` / `ROBOT_DISABLED` (explosion, then removed) / `ROBOT_RESPAWNED` / `CRATE_SPAWNED`. Nothing is predicted: every coordinate is in an event. Intermediate frames are verified in tests to be exact prefixes of the event stream, and the replay must end on the authoritative snapshot (compared field by field, every round of a scripted 2-player round set and of 12-round 4-player bot matches).
* **Phases are distinct.** Order steps highlight the acting robot; machinery steps get an amber board border, a gear queue chip and a "MACHINERY" caption, and belt chevrons only animate then (frozen during order steps). A `WAIT` robot moved by a belt reads "BELT carries P1 (ordered WAIT)".
* **B-03 partly done.** Default pace ≈ 5–8 s for a 2-player round and 10–14 s for 4 players (measured over 12 bot rounds each). `--anim-speed X` sets the speed, `[` / `]` (or `-` / `=`) change it live (0.5×–4×), `Space` or the SKIP button commits all remaining events at once, `--no-anim` disables the replay. Playback is local; the server and other clients never wait for it. Not done: per-event hold tuning beyond the constants in `ui_playback.cpp`.
* **Known limits / observations.**
  * If rounds resolve faster than they play (everyone locks in at once), replays queue up; SKIP clears the whole backlog. The title shows `REPLAY` while a replay is running.
  * The hover read-out and the "your robot" panel describe the authoritative state, not the mid-replay board.
  * Narration lines are released per tick as the replay reaches them; the next round's spawn/respawn lines arrive with the last tick.
  * The match-over overlay waits for the replay to finish.
  * Testing aid: `botched-client --ui --programs "R F2 L;F2 F W;…"` auto-submits scripted orders per round.

## Later — P3: Broader game experience (parked)

- [x] **B-07 — Server-managed bots (done; evidence below).** Support 2–4 seats in any mixture of humans and bots (at least one human), with no separate bot processes. Bots submit normal legal programmes, are imperfect but goal-directed, and use deterministic seeded decisions. Distinct from the `--bot` demo clients (which remain).

  **Design.** `CREATE_MATCH` takes an optional `"bots": 0..3` (must leave a human seat; additive, `botched/1` otherwise unchanged). Bot seats take the highest player ids; the lobby counts them as filled seats (`joined` includes bots, status adds `bots`; after start, `bot_players`). The match starts when the human seats are filled (or START_MATCH with ≥1 human). At the start of every planning phase the server asks each bot for a plan from the **public snapshot only** and submits it through `Match::submit_program` with a normal request id and `ready=true`, so bots are subject to the same rules, budget and idempotency as humans, appear as READY in the scoreboard and replay through the same execution queue/animation. A client cannot submit for a bot seat (`UNAUTHORIZED`). Seeds: `ServerConfig::bot_seed` ⊕ hash(match id, seat). Rooms/humans/lobby code paths are otherwise untouched.

  **Bot logic (`server/bot.{hpp,cpp}`, moved from `apps/`).** Replaces shortest-path-and-hope with a depth-3 search over the bot's own orders (7 options per slot) that scores each candidate by running the **real engine** on a copy of the snapshot's world (opponents assumed to WAIT) plus one extra machinery tick: delivery ≫ crate pickup ≫ progress (walking distance to the nearest loose crate, or to its own dock when carrying), heavy penalties for pits, laser damage and being carried into trouble by a belt, small penalty for loitering on belts. Imperfection: seeded score noise, a 12 % chance per round of choosing among the top 30 programmes, and a 10 % chance per slot of a random order ("fumble"). Falls back to the old path planner if the snapshot cannot be read. ≈4–7 ms per plan.

  **Client/UI.** `botched-client --create --players N --bots M` (text and SDL). SDL lobby text shows `N of M seats filled (K bots)`; scoreboard cards show `P3 BOT`. Nothing else in the lobby or scoreboard changed.

  **Evidence.**
  * Tests (`tests/test_bots.cpp`, 4 cases): seat rules (≥1 human, bot counts, lobby counts, autostart when humans are in, no extra human seat), bots lock in each round while the humans are the only ones waited for, a client cannot drive a bot seat, full 12-round matches 1 human + 3 bots / 2 humans + 2 bots / 1 + 1 complete and are identical for the same seed (different seed → different match), and across 6 seeded matches 3 bots deliver ≥ 6 crates per match in total and fall into pits at most once per match on average. Full suite 186 cases pass; also clean under ASan+UBSan.
  * Bot quality (10 seeded 12-round matches, all-bot, measured): old planner ≈ 1–3 deliveries per player per match; new bot **4.6 (2 players) / 3.7 (4 players) deliveries per player**, 0.1–0.2 robots disabled per match (tuned from 7.4 / 5.5 for a perfect bot, so humans can compete).
  * Rules untouched: with the old planner temporarily restored the pre-B-07 simulator hashes (`e846c1c016b36358` / `5d9ebce915bed1f8`) still reproduce exactly. They are re-pinned to the new bot's output (`8b9b82fb718c2751` / `415308a3742c5db6`) in `tests/test_idempotency.cpp`.
  * Demo 1, one human seat vs three server bots (real `botched-tcp-server` + `botched-client --create --players 4 --bots 3`, 12 rounds): finished, P1 25 pts (5 deliveries), P2 25 (5), P3 10 (2), **P4 35 (7) wins**. Demo 2, two human-seat clients vs two server bots (`--create --players 4 --bots 2` + `--join`): both clients finished and agreed, P4 (a bot) won. SDL screenshots of both modes show `BOT` tags and the bots' orders/moves/deliveries in the execution queue and replay (e.g. "P4 DELIVERS crate 4").
  * Known limits: bots assume opponents WAIT and do not use DROP/TOGGLE; no bot names or difficulty levels; a bot-only lobby cannot be created (≥1 human).
